# 技術構成と設計判断

FSRSアルゴリズムを用いた学習スケジュール管理アプリの、技術選定とその理由をまとめたもの。

- 本番: https://study-scheduler-lemon.vercel.app
- ソース: 約2,600行(TypeScript)/ 依存パッケージ7個

---

## 1. 何を作ったか

### 解決したい問題

演習問題を解いても、**いつ復習すべきかは自分では判断できない**。早すぎれば時間の無駄、遅すぎれば忘れている。人間の記憶は指数的に減衰するため、感覚的な「そろそろやるか」は最適から大きく外れる。

### アプローチ

**間隔反復(Spaced Repetition)** — 忘れかけたタイミングで復習すると記憶が最も定着する、という性質を利用する。問題を解いたときの出来を4段階で記録し、そこから次に復習すべき日を自動算出する。

アルゴリズムには **FSRS (Free Spaced Repetition Scheduler)** を採用した。Ankiが標準採用しているもので、記憶を以下の3つの量でモデル化する。

| 量 | 意味 |
|---|---|
| Stability (S) | 記憶の持続力。「思い出せる確率が90%まで落ちるのに何日かかるか」 |
| Difficulty (D) | その項目の難しさ(1〜10) |
| Retrievability (R) | 現在の想起確率。時間とともに減衰する |

`R` が設定した目標値まで落ちた日を復習日とする。次の間隔は

```
I = (R^(1/DECAY) - 1) / FACTOR × S
```

で決まり、S と D は復習のたびに更新される。同じ「できた」を押しても、その項目の履歴によって次回が3日後にも586日後にもなる。

## 2. 全体構成

```
┌─────────────────────────────────────────┐
│  ブラウザ (PC / スマホ / iPad)            │
│  ・PWA としてホーム画面に追加可能           │
└───────────────┬─────────────────────────┘
                │ HTTPS
┌───────────────▼─────────────────────────┐
│  Vercel                                  │
│  ┌────────────────────────────────────┐ │
│  │ Next.js 16 (App Router)            │ │
│  │  Server Components  … 画面描画      │ │
│  │  Server Actions     … 更新処理      │ │
│  │  proxy.ts           … 認証ガード     │ │
│  │  ts-fsrs            … 復習日の算出   │ │
│  │  binding (Rust)     … パラメータ最適化│ │
│  └────────────────────────────────────┘ │
└───────────────┬─────────────────────────┘
                │ PostgreSQL wire / REST
┌───────────────▼─────────────────────────┐
│  Supabase                                │
│  ・PostgreSQL (Row Level Security)       │
│  ・Auth (メール + パスワード)              │
└─────────────────────────────────────────┘
```

処理の流れ(復習を記録する場合):

1. ブラウザで評価ボタンを押す
2. Server Action `submitReview` が呼ばれる
3. DBから現在のFSRS状態を取得
4. `ts-fsrs` が次の状態(次回日・S・D)を算出
5. `review_states` を更新し、`review_logs` に履歴を追加
6. `revalidatePath` で画面を再描画

## 3. 技術選定

### Next.js 16 (App Router)

**何か**: Reactベースのフルスタックフレームワーク。サーバー側での描画と、APIエンドポイントの両方を1つのプロジェクトで扱える。

**なぜ選んだか**

このアプリは「DBから取ってきて表示する」処理が大半を占める。App Routerの **Server Components** を使うと、この処理をサーバー側で完結できる。

```tsx
// app/page.tsx — これがそのままサーバーで動く
export default async function HomePage() {
  const dueItems = await getDueItems();   // DBに直接問い合わせ
  return <ul>{dueItems.map(...)}</ul>;    // HTMLを返す
}
```

得られた利点:

- **APIエンドポイントを書かなくてよい**。`/api/items` のようなルートと、それを呼ぶ `fetch` の両方が不要になる
- **クライアントの状態管理が要らない**。当初 TanStack Query を入れたが、サーバー側で完結したため一度も使わず削除した
- **JavaScriptを送る量が減る**。クライアントコンポーネントは `ItemRow.tsx` と `ReviewButtons.tsx` の2つだけ

更新処理は **Server Actions** で書いた。フォームの `action` に関数を直接渡せる。

```tsx
<form action={addSolvedItem}>   // サーバー関数を直接指定
```

**代替案との比較**

| 候補 | 見送った理由 |
|---|---|
| React (SPA) + 別途API | APIサーバーを別に立てる必要があり、個人開発には過剰 |
| SvelteKit | より軽量だが、情報量とエコシステムでNext.jsが優位 |

**苦労した点**: Next.js 16 で `middleware.ts` が `proxy.ts` に改称された。古い名前のままだと**エラーも警告も出ずに無視され、認証ガードが静かに機能しなくなる**。ビルド時の非推奨警告に気づいて移行した。

### Supabase (PostgreSQL + Auth)

**何か**: PostgreSQLに認証機能などを組み合わせたBaaS(Backend as a Service)。

**なぜ選んだか**

**1. データがリレーショナルだから**

項目・現在の状態・復習履歴は明確な1対1、1対多の関係にある。「期日が来た項目を取得」「日別の復習回数を集計」といった処理はSQLで素直に書ける。

**2. Row Level Security (RLS) を使いたかったから**

これが決め手になった。RLSは**「誰がどの行を見られるか」をDB自身に強制させる**PostgreSQLの機能。

```sql
create policy "items_select_own" on public.items
  for select using (auth.uid() = user_id);
```

このポリシーがあると、アプリ側で `where user_id = ...` を書き忘れても他人のデータは返らない。**アプリのバグでは破れない**ため、認可の判断がDB1箇所に集約される。

実際に検証した結果:

```
未ログインでの読み取り → [] (空)
未ログインでの書き込み → HTTP 401 で拒否
```

**代替案との比較**

| 候補 | 見送った理由 |
|---|---|
| Firebase (Firestore) | NoSQLで非正規化が前提。復習履歴の集計に向かない |
| 自前のDB + 認証 | 認証の自前実装は脆弱性の温床。個人開発で背負うリスクが大きい |

### ts-fsrs

**何か**: FSRSアルゴリズムのTypeScript実装。開発元は本家のFSRSコミュニティ。

**なぜ自作しなかったか**: FSRSは21個のパラメータを持つ記憶モデルで、それらは数百万件のAnki利用者のログから機械学習で決められている。自作しても精度で勝てず、車輪の再発明になる。

**設定を1つ変えた**

```ts
const scheduler = fsrs({ enable_short_term: false });
```

既定では「1分後 → 10分後」という当日中の再出題ステップが入る。これは単語カードを反復して覚える使い方を想定した設定で、**演習問題を10分後にもう一度解くのは非現実的**。無効にして最短でも翌日以降になるようにした。

| 設定 | 新規項目で「できた」を押した後の間隔 |
|---|---|
| 既定 | 10分 → 2日 → 11日 → 46日 |
| 無効化後 | 3日 → 14日 → 57日 → 196日 |

### @open-spaced-repetition/binding (Rust)

**何か**: FSRSのパラメータ最適化器。Rustで書かれ、Node.jsから呼べるようバインディングされている。

**なぜ必要か**: `ts-fsrs` はスケジューリングのみで、パラメータの学習機能を持たない。既定パラメータは他人のデータで学習されたものなので、自分の記憶特性に合わせて再調整するには別途これが要る。

**仕組みを調べて分かったこと**

ソースを読むと、これは「ゼロから学習」ではなく**既定値からのファインチューニング**だった。

```rust
let training_initial_parameters = model_config.initial_parameters();  // 既定値から出発
add_l2_gradient(&parameters, initial_parameters, ...);                // 既定値へ引き戻す
```

L2正則化が既定値からの逸脱にペナルティをかけるため、**データが少ないほど既定値の近くに留まる**。導入したPRの説明も「少数レビューのユーザーに対して最適化を保守的にするため」だった。

実測でも、20アイテムでは既定値からの変化量が **0.000** だった(64件未満は学習を省略する早期リターンがあるため)。この閾値をアプリ側の下限にも採用した。

### Tailwind CSS

**何か**: ユーティリティクラスでスタイルを当てるCSSフレームワーク。

**なぜ選んだか**: スマホ・タブレット・PCで表示を変える必要があり、`sm:` `md:` といった接頭辞でブレークポイントを書き分けられる点が要件に合った。

**shadcn/ui を導入したが撤去した**: UIコンポーネント集を入れたものの、実際に必要だったのは入力欄・ボタン・リストといった基本要素だけで、生成されたコンポーネントを一度も使わなかった。**依存を8個削除**し、`globals.css` も130行から25行にした。

## 4. データ設計

```
auth.users (Supabase管理)
     │
     ├──< items              演習項目(タイトル・科目)
     │        │
     │        ├──1:1── review_states   現在のFSRS状態
     │        └──1:N── review_logs     復習履歴(追記のみ)
     │
     └──1:1── user_settings   目標保持率・個人最適化パラメータ
```

**`review_states` と `review_logs` を分けた理由**

- `review_states` は**現在の状態**。`ts-fsrs` の `Card` 型をほぼそのまま保存し、次回の算出に使う
- `review_logs` は**追記専用の履歴**。統計・グラフ・個人最適化の学習データはすべてこちらから作る

状態と履歴を分けたことで、統計機能や最適化機能を後から追加する際にスキーマを変更せずに済んだ。

**カスケード削除**

```sql
item_id uuid references public.items(id) on delete cascade
```

項目を消せば状態も履歴も自動で消える。アプリ側で子テーブルを消す処理は書いていない。

なお `review_logs` にDELETEポリシーは定義していないが、PostgreSQLの仕様上これで問題ない。

> Referential integrity checks, such as unique or primary key constraints and foreign key references, always bypass row security
> — PostgreSQL公式ドキュメント

参照整合性によるカスケードはRLSをバイパスするため、親の削除権限(`items_delete_own`)だけで完結する。

## 5. 実装で判断が必要だった点

### サーバーのタイムゾーン

Vercelのサーバーは **UTC** で動く。素直に日付を扱うと、**日本時間の0時〜9時が前日として集計される**。カレンダーの表示や日別グラフが1日ずれる。

`Asia/Tokyo` 固定の変換を1箇所に集約して解決した。

```ts
const dayKeyFormatter = new Intl.DateTimeFormat("en-CA", {
  timeZone: "Asia/Tokyo", year: "numeric", month: "2-digit", day: "2-digit",
});
export function toDayKey(date: Date): string {
  return dayKeyFormatter.format(date);
}
```

### JSから捕捉できないクラッシュ

最適化器に不正な入力を渡すと、Rust側でパニックが起きる。

```
Invalid FSRS item: at least one review with delta_t > 0 is required
panic in a function that cannot unwind → aborting
```

これは **`try/catch` で捕まえられず、プロセスごと落ちる**。サーバーレス環境で起きればサーバーエラーになる。

原因は「復習が1回だけの項目」を学習データに含めていたこと。FSRSの学習データは「経過日数が0より大きい復習」を最低1つ含む必要がある。渡す前に検証する処理を入れ、境界ケース4種で確認した。

| 入力 | 期待 | 結果 |
|---|---|---|
| 1回しか復習していない項目 | 0件 | 0件 |
| 同日に3連打しただけ | 0件 | 0件 |
| 3回(日をあけて) | 2件 | 2件 |
| 複数項目が混在 | 有効なものだけ | 一致 |

### 検証できない時期があることへの対処

個人最適化は学習データが64件溜まらないと実行できず、実際に使えるのは数か月先になる。そのときに初めて「Vercel上でネイティブモジュールが読めない」と判明しても遅い。

合成データで実行経路だけを検証する**自己診断機能**を用意し、本番環境での動作をその場で確認できるようにした。

### グラフをSVGからHTMLに書き換えた

当初SVGで描いていたが、`viewBox` をCSSで伸縮させる方式のため、**幅328pxのスマホでは0.55倍に縮み、10pxの軸ラベルが実質5.5pxになる**問題があった。スマホ利用が主目的なので致命的だった。

HTML/CSSでの描画に切り替え、文字は通常のレスポンシブ指定が効くようにした。配色は色覚特性とコントラスト比の検証スクリプトを通し、ライト・ダーク両モードで基準を満たすことを確認している。

### UIの無駄を削った

当初は「項目管理ページで登録 → ホームに移動 → 評価を押す」という2画面2アクションだった。

しかし**追加する時点で既に問題を解き終わっている**のだから、登録と初回評価を分ける理由がない。1つのフォームにまとめ、評価ボタン自体を送信ボタンにした。ページも統合し、`/items` の一覧は廃止した。

## 6. セキュリティ

| 対策 | 内容 |
|---|---|
| Row Level Security | 全テーブルで有効。`auth.uid() = user_id` の行のみ操作可 |
| APIキーの種別 | ブラウザに配るのは publishable key のみ。RLSを無視できる secret key は使わない |
| 認証ガード | `proxy.ts` で未ログインを `/login` へリダイレクト |
| 新規登録 | 個人利用のため無効化。招待は管理画面から個別に行う |
| 秘密情報 | `.env.local` は `.gitignore` 済み。コミット前に毎回スキャン |

## 7. 検討して見送ったこと

### 科目ごとにFSRSパラメータを分ける

「数学とSPIでは記憶の特性が違うはずだから、科目ごとに別々のパラメータを最適化してはどうか」という案を検討した。**発想自体は正当で、Ankiが実際に採用している方式**と一致する。

> If you have decks that vary wildly in subjective difficulty, it is recommended to assign them separate presets
> — [Anki Manual, Deck Options](https://docs.ankiweb.net/deck-options.html)

Ankiではパラメータをプリセット(≒科目)単位で持てる。FSRSのFAQも「日本語と地理を学ぶなら2つのプリセットに分けるべき」と明示している。

**しかし実測すると効果はほぼない。** 9,999コレクション・3.5億レビューの公開ベンチマーク:

| 方式 | RMSE(小さいほど良い) | AUC(大きいほど良い) |
|---|---|---|
| コレクション全体で1つ | 0.0655 | 0.7069 |
| プリセット別(科目別) | 0.0650 | 0.7079 |
| デッキ別(さらに細かく) | 0.0725 | 0.7016 |

改善したのは利用者の57.1%で、開発者の評価も "very mildly better. By an imperceptible-in-practice amount."。しかも**細かく分けすぎると明確に悪化する**(デッキ別)。

一方で実装と運用の複雑さは実在する。科目ごとのパラメータ保存(スキーマ変更)、科目ごとの最適化UI、タグが無い項目の扱い、科目名を変更・統合したときの引き継ぎ。**知覚できない改善のために背負うコストとして見合わない**と判断した。

**当初の懸念は誤りだった** — 検討の初期に「科目5つなら1000件×5のデータが必要になる」と考えたが、これは事実に反していた。Anki 24.06.3 以降は最小レビュー数の制限が撤廃されており、`fsrs-rs` のL2正則化は `gamma * batch_size / total_size` でスケールするため、**データが少ないプリセットは自動的に既定値へ強く引き戻される**。分割してもデータ不足による過学習は構造的に抑制される。

**将来分けるべき状況を見分ける基準** — FSRSの難易度は1〜10で頭打ちになる。ある科目の項目が軒並み難しいと難易度が上限に張り付き、それ以上の調整ができなくなる。この飽和が起きていれば分割の意味がある。項目詳細ページの難易度を見れば判断できる。

ただし根拠は個人の事例(n=1、対照実験なし)であり、「単語暗記と問題演習でパラメータが有意に異なる」という直接的なデータは見つかっていない。FSRS開発者自身も、分けるべきかの客観的な判定方法は確立していないと述べている。

出典: [srs-benchmark](https://github.com/open-spaced-repetition/srs-benchmark) / [Anki FSRS FAQ](https://faqs.ankiweb.net/frequently-asked-questions-about-fsrs.html) / [fsrs-rs training.rs](https://github.com/open-spaced-repetition/fsrs-rs/blob/main/src/training.rs)

**ただし目標保持率の科目別設定は採用した** — 21個のパラメータとは性質が異なる。保持率は履歴から学習する値ではなく**単なる設定値**なので、データ量の問題が一切ない。「この科目をいまどれだけ優先したいか」という利用者の意思をそのまま表す。Ankiでも保持率はプリセット単位で持てる。

実装時、想定していなかったことが分かった。**当初 0.95 を「試験前用」として用意していたが、短期間では効果がない。** 試験まで23日として復習が回る回数を計算すると:

| 保持率 | 復習回数 | 復習が入る日 |
|---|---|---|
| 0.90 | 3回 | 0, 3, 17日目 |
| 0.95 | 3回 | 0, 3, 9日目 |
| 0.97 | 4回 | 0, 3, 6, 12日目 |
| 0.99 | 7回 | 0, 3, 6, 9, 12, 16, 21日目 |

0.90 と 0.95 は回数が同じで、差が出るのは 0.97 から。UIに数値を並べるだけでは「0.95にすれば試験対策になる」と誤解させるので、選択肢に 0.97 / 0.99 を足し、この表を設定画面に表示するようにした。

## 8. 今後の課題

- **個人最適化の実効果が未検証** — 学習データが64件に達していないため、既定値から実際にどれだけ改善するかは未確認
- **自動テストがない** — 現状は手動確認とビルド時の型チェックのみ。FSRSの状態遷移や日付変換は単体テストを書く価値がある
- **教材の共有機能がない** — 各ユーザーが完全に分離されており、同じ問題集を使う相手と項目を共有できない
