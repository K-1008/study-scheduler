# このアプリで学ぶWeb開発の基礎

開発経験がない状態から、このアプリが何をしているのかを理解するための文書。
専門用語は初出時に必ず説明する。実際のファイルを指しながら進めるので、
手元でコードを開きながら読むとよい。

---

## 第1部 Webアプリを開いたとき何が起きているか

### 登場人物は3つ

スマホで `https://study-scheduler-lemon.vercel.app` を開いたとき、次の3者がやり取りしている。

```
[あなたのブラウザ]  ←→  [サーバー]  ←→  [データベース]
   Safari/Chrome         Vercel          Supabase
```

**ブラウザ** — 画面を表示する。あなたの手元で動く。

**サーバー** — インターネット上にある、24時間動いているコンピュータ。ブラウザから「このページをください」と頼まれたら、中身を作って返す。今回は **Vercel** という会社のサーバーを借りている。

**データベース** — データを保存しておく専用のソフトウェア。「あなたの演習項目は何件で、次回はいつか」を覚えている。今回は **Supabase** という会社のものを借りている。

### 実際の流れ

「今日の復習」で「できた」を押したとき、こう動く。

```
1. ブラウザ    「この項目、できたそうです」            → サーバー
2. サーバー    「この項目の今の状態を教えて」          → データベース
3. データベース「安定度2.31、難易度2.12、前回8/7」    → サーバー
4. サーバー    FSRSで計算 →「次回は3日後だ」
5. サーバー    「状態を更新して、履歴も1件追加して」  → データベース
6. サーバー    新しい画面のHTMLを作る                 → ブラウザ
7. ブラウザ    「記録しました。次回は3日後です」と表示
```

**重要な点**: 計算(4)はサーバーで行っている。ブラウザ側ではやっていない。

なぜか。ブラウザで動くコードは、利用者が自由に書き換えられるから。「次回は10年後」と偽装されても困る。**信用できない場所で大事な処理をしない**、というのがWeb開発の基本的な考え方。

### フロントエンドとバックエンド

- **フロントエンド** — ブラウザ側。見た目、ボタン、入力欄
- **バックエンド** — サーバー側。計算、データベースとのやり取り、認証

このアプリでは Next.js が両方を担当している。こういうものを **フルスタックフレームワーク** と呼ぶ。

## 第2部 使っている技術の意味

### フレームワークとは何か

**やりたいことの土台を用意してくれる道具一式**のこと。

Webアプリを何もない状態から作るとなると、こういうものを全部自分で書く必要がある。

- ブラウザからの通信を受け取る仕組み
- URLごとに違う処理を振り分ける仕組み(`/settings` なら設定画面、など)
- HTMLを組み立てる仕組み
- ファイルを更新したら自動で反映する仕組み

これらは**どのWebアプリでも同じ**なので、毎回書くのは無駄。フレームワークがまとめて用意してくれる。

今回は **Next.js**(ネクストジェイエス)を使っている。

### React と Next.js の関係

**React**(リアクト)— 画面を「部品」の組み合わせで作るための道具。Facebookが作った。

例えばこのアプリの `app/Nav.tsx` は画面上部のナビゲーション部分を作る部品。他のページから呼び出せば、同じものが表示される。

```tsx
export async function Nav() {
  return (
    <header>
      <Link href="/">ホーム</Link>
      <Link href="/calendar">カレンダー</Link>
    </header>
  );
}
```

HTMLに似ているが、これはJavaScriptのコード。この書き方を **JSX** という。

**Next.js** — Reactを使ったアプリを実際に運用できる形にするための土台。Reactだけでは足りないもの(サーバー側の処理、URLの振り分け、本番向けの最適化)を補う。

**関係**: React が「画面の作り方」、Next.js が「アプリ全体の作り方」。

### App Router — URLがフォルダ構造になる

Next.js では、**フォルダの構造がそのままURLになる**。

```
app/page.tsx              →  /            (ホーム)
app/calendar/page.tsx     →  /calendar    (カレンダー)
app/settings/page.tsx     →  /settings    (設定)
app/items/[id]/page.tsx   →  /items/xxxx  (項目の詳細)
```

`[id]` の角括弧は「ここは可変」という意味。`/items/abc123` でも `/items/def456` でも、同じ `page.tsx` が動き、`id` の中身だけが変わる。

この仕組みを **App Router** と呼ぶ。

### Server Components — サーバーで動く画面

普通のReactは、ブラウザ側で画面を組み立てる。Next.js の **Server Components** は、**サーバー側で組み立ててHTMLとして送る**。

`app/page.tsx` を見てほしい。

```tsx
export default async function HomePage() {
  const dueItems = await getDueItems();     // ← データベースに直接聞いている
  return <ul>{dueItems.map(...)}</ul>;      // ← HTMLを組み立てて返す
}
```

`getDueItems()` はデータベースへの問い合わせ。**これがブラウザ側だったら書けない**。データベースのパスワードをブラウザに置くことになってしまうから。サーバーで動くからこそ、こう書ける。

**利点**: 通常なら「APIを作って、ブラウザからそれを呼ぶ」という2段構えが必要なところを、1つの関数で済ませられる。

> 用語: **API** (Application Programming Interface) — プログラム同士がやり取りするための窓口。「この住所に、この形式で頼めば、この形式で返す」という約束事。

### Server Actions — サーバーで動く更新処理

画面を表示するだけでなく、データを更新するときにも同じ考え方を使う。

`app/items/actions.ts` の先頭にこう書いてある。

```ts
"use server";
```

これは「このファイルの関数はサーバーで動く」という宣言。そしてフォームから直接呼べる。

```tsx
<form action={addSolvedItem}>
  <input name="title" />
  <button type="submit">できた</button>
</form>
```

ボタンを押すと、`addSolvedItem` がサーバーで実行される。ブラウザ側に通信のコードを書く必要がない。

### クライアントコンポーネント — ブラウザで動く部品

とはいえ、ブラウザ側でしかできないこともある。

- ボタンを押した瞬間に見た目を変える
- 確認ダイアログを出す
- 入力途中の状態を覚えておく

そういう部品は先頭に `"use client"` と書く。このアプリでは2つだけ。

- `app/ItemRow.tsx` — 「編集」を押すと入力欄に切り替わる
- `app/reviews/ReviewButtons.tsx` — 押した後に「次回は3日後」と表示する

**なぜ2つだけなのか**: ブラウザに送るコードが減るほどページの表示が速くなる。サーバーで済むことはサーバーでやる、という方針にしている。

## 第3部 データベースの話

### データベースとは

データを保存・検索するための専用ソフトウェア。「ファイルに保存すればいいのでは」と思うかもしれないが、次のような要求に応えるのが難しい。

- 「期日が今日以前の項目だけ、期日が近い順に取り出す」
- 「同時に2人が更新しても壊れない」
- 「他人のデータは絶対に見せない」

データベースはこれらを担当する。今回使っているのは **PostgreSQL**(ポストグレスキューエル)。

### テーブル — 表形式でデータを持つ

データベースは**表(テーブル)**の集まり。このアプリには4つある。

**`items`** — 演習項目

| id | user_id | title | tag |
|---|---|---|---|
| abc123 | you | 積分の応用問題 第3章 | 数学 |
| def456 | you | SPI 非言語 | 就活 |

**`review_states`** — 各項目の現在の状態(1項目につき1行)

| item_id | due | stability | difficulty |
|---|---|---|---|
| abc123 | 2026-08-10 | 2.31 | 2.12 |

**`review_logs`** — 復習の履歴(1回の復習につき1行、増える一方)

| id | item_id | rating | reviewed_at |
|---|---|---|---|
| log1 | abc123 | 3 | 2026-08-07 |
| log2 | abc123 | 1 | 2026-08-09 |

**`user_settings`** — 設定(1人につき1行)

### なぜ表を分けるのか

すべて1つの表に入れることもできるが、そうしない。

`items` と `review_states` を分けた理由は**役割が違う**から。前者は「何を勉強するか」で滅多に変わらない。後者は「いまどういう記憶状態か」で復習のたびに変わる。

`review_logs` を分けた理由は**性質が違う**から。これは過去の記録なので書き換えない。追加だけ。統計グラフも個人最適化の学習データも、すべてここから作る。

> 用語: **正規化** — データの重複をなくすように表を分ける設計手法。

### リレーション — 表と表のつながり

`review_states` の `item_id` は `items` の `id` を指している。この「指している」関係を **外部キー(Foreign Key)** と呼ぶ。

```sql
item_id uuid references public.items(id) on delete cascade
```

`on delete cascade` は「親が消えたら自分も消える」という指定。項目を削除すると、その状態と履歴も自動的に消える。アプリ側で消す処理を書かなくてよい。

### SQL — データベースへの命令文

データベースには **SQL**(エスキューエル)という言語で命令する。

```sql
select title from items where tag = '数学';
```

「`items` から、`tag` が数学のものの `title` を取ってこい」という意味。

ただしこのアプリのコードにSQLはほとんど出てこない。Supabaseのライブラリが、JavaScriptの書き方をSQLに翻訳してくれるから。

```ts
supabase.from("items").select("title").eq("tag", "数学")
```

`supabase/migrations/` の中にはSQLが直接書いてある。ここは**表を作る**という、アプリ起動前の準備作業なので、SQLで書く。

> 用語: **マイグレーション** — データベースの構造を変更する作業とその記録。ファイルに残しておけば、別の環境でも同じ構造を再現できる。

## 第4部 認証と認可 — このアプリの肝

用語が2つある。混同しやすいので分けて覚える。

- **認証 (Authentication)** — **あなたが誰か**を確かめること。ログイン
- **認可 (Authorization)** — **何をしてよいか**を決めること。権限

### 認証の仕組み

1. メールアドレスとパスワードを送る
2. Supabaseが照合し、合っていれば **トークン** を発行する
3. ブラウザはトークンを保存する(Cookieという仕組み)
4. 以降のやり取りでは毎回トークンを送る。サーバーは「これはあの人だ」と分かる

> 用語: **トークン** — ログイン済みであることを証明する文字列。入館証のようなもの。

### 認可の仕組み — Row Level Security

ここがこのアプリで**最も重要な設計判断**。

普通のやり方だと、アプリのコードでこう書く。

```ts
// 「自分のものだけ」という条件を毎回書く
supabase.from("items").select("*").eq("user_id", 自分のID)
```

問題は、**1箇所でも書き忘れたら他人のデータが漏れる**こと。しかも書き忘れてもエラーにならず、動いてしまう。

**Row Level Security (RLS)** は、この判断をデータベース自身にさせる仕組み。

```sql
create policy "items_select_own" on public.items
  for select using (auth.uid() = user_id);
```

「`items` を読むときは、`user_id` がログイン中の人と一致する行だけ返す」というルール。**データベースがこれを強制する**ので、アプリ側が条件を書き忘れても他人のデータは返らない。

実際に試すとこうなる。

```
未ログインで読み取り  → [] (空っぽ)
未ログインで書き込み  → HTTP 401 (拒否)
```

**面接で聞かれたらこう答えられる**: 「認可の判断をアプリ側に散らすと、書き忘れが即座に情報漏洩につながる。DB層に寄せてしまえば、アプリにバグがあっても破れない」

### APIキーの使い分け

Supabaseに接続するには鍵が要る。2種類ある。

| 鍵 | 性質 | 用途 |
|---|---|---|
| publishable key | RLSが効く | ブラウザに配ってよい |
| secret key | **RLSを無視する** | サーバー内部のみ。絶対に外に出さない |

このアプリは publishable key しか使っていない。RLSが全アクセスを本人の行に制限するので、ブラウザに配っても安全。

## 第5部 開発を支える道具

### Git と GitHub

**Git**(ギット)— ファイルの変更履歴を記録する道具。「いつ・何を・なぜ変えたか」を残せる。間違えたら過去に戻せる。

基本の流れ。

```bash
git add -A                    # 変更したファイルを選ぶ
git commit -m "○○を修正"      # 履歴として記録する
git push                      # GitHubに送る
```

> 用語: **コミット** — 変更を1つのまとまりとして記録すること。「なぜそう変えたか」を書き残す場所でもある。

**GitHub**(ギットハブ)— Gitの記録をインターネット上に置いておくサービス。バックアップになり、他人に見せられる。

このアプリには現在16件のコミットがある。「アーカイブを廃止し、一覧からの編集と完全削除を追加」のように、**何をなぜ変えたか**を書いてある。採用担当者が見るのはコードだけでなく、この履歴でもある。

### npm とパッケージ

**パッケージ**(ライブラリとも)— 他人が作った再利用可能なコードのまとまり。

例えばFSRSのアルゴリズムは複雑な数式の塊だが、`ts-fsrs` というパッケージを使えば自分で実装しなくてよい。

**npm**(エヌピーエム)— パッケージを導入・管理する道具。

```bash
npm install ts-fsrs      # 導入する
npm run dev              # 開発用にアプリを起動する
npm run build            # 本番用に組み立てる
```

`package.json` に、このアプリが使っているパッケージが書いてある。現在7個。

> **注意**: 使っていないパッケージを放置しない。当初15個入っていたが、実際に使っていたのは7個だった。「なぜこれが入っているのか」に答えられない状態は避ける。

### TypeScript — 型のあるJavaScript

**JavaScript** — ブラウザで動く言語。Node.jsという実行環境を使えばサーバーでも動く。

**TypeScript** — JavaScriptに **型** を足したもの。

型とは「この変数には何が入るか」の宣言。

```ts
function describeInterval(due: Date, from: Date): string
//                            ^^^^        ^^^^   ^^^^^^
//                          Date型を2つ受け取り、文字列を返す
```

**何が嬉しいか**: 間違いをプログラムを動かす前に見つけられる。`due` に数字を渡そうとすると、その場でエラーになる。

このアプリで `npm run build` を実行すると型チェックが走る。通らなければ本番に出せない仕組みになっている。

### デプロイ

**デプロイ** — 作ったものを、インターネット上で使える状態にすること。

このアプリは GitHub に `git push` すると、Vercel が自動的に受け取って本番に反映する。

```
手元で編集 → git push → GitHub → Vercel が検知 → ビルド → 公開
```

> 用語: **ビルド** — 書いたコードを、実際に動く形に変換する作業。TypeScriptをJavaScriptに変換したり、まとめて圧縮したりする。

### 環境変数

データベースのURLや鍵を、コードに直接書いてはいけない。GitHubに公開したら鍵が漏れるから。

そこで **環境変数** という仕組みを使う。設定値をコードの外に置く。

```
.env.local    ← ここに書く。Gitには含めない(.gitignore で除外)
```

本番では Vercel の管理画面に同じ値を登録している。

> 用語: **.gitignore** — Gitに記録させないファイルを指定する設定ファイル。パスワードや、自動生成される巨大なフォルダ(`node_modules`)を除外する。

## 第6部 このアプリ特有の技術

### FSRS — 何をしているアルゴリズムか

人間の記憶は時間とともに指数的に減衰する。この減衰を数式でモデル化し、**忘れかける直前**に復習日を設定する。

3つの量で記憶を表す。

- **安定度 (Stability)** — 記憶の持ちの良さ。「思い出せる確率が90%に落ちるまでの日数」
- **難易度 (Difficulty)** — その項目の難しさ(1〜10)
- **想起率 (Retrievability)** — 今すぐ思い出せる確率。時間とともに下がる

「できた」を押すと安定度が上がり、次回までの間隔が伸びる。「できない」を押すと安定度が下がり、間隔が縮む。

実際に計算するとこうなる。

```
A: 「できた」を4回     → 次回586日後  (安定度196.2)
B: 「できない」混じり  → 次回4日後    (安定度1.6)
```

**同じボタンを押しても、履歴によって146倍の差が出る**。これが「一律に何日後」ではないということ。

### 個人最適化 — 機械学習の部分

FSRSには21個のパラメータ(係数)がある。既定値は数百万件のAnki利用者のログから機械学習で求められたもの。

これを**自分のデータで微調整**できる。ただし、やり方に工夫がある。

- ゼロから学習するのではなく、**既定値を出発点にする**
- 既定値から離れすぎないようペナルティをかける(**L2正則化**)
- データが64件未満なら学習を省略する

つまり**データが少ないうちは既定値のまま、増えるほど自分向きに寄る**。少ないデータで大きく動くと、たまたまの結果に振り回されてかえって精度が落ちるため。

> 用語: **過学習 (overfitting)** — 手元の少ないデータに合わせすぎて、未知のデータに対応できなくなること。機械学習で最も基本的な失敗。

## 次にやるとよいこと

1. **この文書を読みながら実際のファイルを開く**。`app/page.tsx` から始めるとよい
2. **小さな変更を自分で加えてみる**。ボタンの文言を変えて `git push` し、本番に反映されるのを確認する
3. **わからない箇所を具体的に質問する**。「`app/reviews/actions.ts` の12行目が何をしているか分からない」のように、ファイルと行を指定すると答えやすい

理解できていない部分を無理に語ろうとせず、**「ここは分かる、ここはまだ分からない」を正確に把握しておく**ことが、面接では最も安全で誠実な状態になる。
